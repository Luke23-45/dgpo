### **Phase 1: Understanding the Diffusion Policy's Data Requirements**

Before modifying any code, we must deeply understand the data needs of our target model. A diffusion policy learns to denoise a sequence of random actions into a coherent, goal-conditioned action plan. This has specific implications for the training data format.

**1. Data Modality: Delta Actions**
*   **Requirement**: The model must be trained on **delta actions**, representing the change in state from one timestep to the next. Our `ScriptedExpert` and `IKSolver` already generate these, but the dataset must be configured to exclusively save and yield this format.
*   **Action Space**: The delta action is an 8-dimensional vector: 7 for the arm's joint position changes and 1 for the gripper state. These actions must be consistently normalized to `[-1, 1]`.

**2. Data Structure: Observation and Action Horizons (Chunking)**
*   **Requirement**: Diffusion policies do not operate on single `(obs, action)` pairs. They require a **history of observations** to infer velocity and momentum, and they predict a **horizon of future actions** to produce smooth, non-myopic behavior.
*   **Observation Horizon (`history_len`)**: Each training sample must include a sequence of the `N` most recent observations.
    *   *Example*: `N=4` means each sample provides the observations from timesteps `t-3`, `t-2`, `t-1`, and `t`.
*   **Action Horizon (`future_len`)**: Each training sample must include the sequence of the `K` subsequent actions that the expert took.
    *   *Example*: `K=8` means each sample provides the ground-truth expert actions for timesteps `t`, `t+1`, ..., `t+7`.

**3. Final Sample Structure**
*   **Requirement**: Each sample yielded by the `ExpertDataset` should be a dictionary containing these chunks, ready for training.
*   **Proposed Structure**:
    ```
    {
        # Shape: (history_len, H, W, C)
        "image_primary_chunk": <torch.Tensor>,

        # Shape: (history_len, proprio_dim)
        "proprio_chunk": <torch.Tensor>,

        # Shape: (future_len, action_dim)
        "action_chunk": <torch.Tensor>
    }
    ```
    *This structured, chunk-based format is the single most important requirement.*

**4. Data Quality and Consistency**
*   **Requirement**: The dataset must consist of **complete and successful trajectories only**. A diffusion model trained on failed or incomplete attempts will learn suboptimal behaviors.
*   **Requirement**: The data must be generated with a consistent simulation `dt` and control frequency, as the magnitude of the delta actions is directly tied to this frequency.

### **Phase 2: Gap Analysis of the Current `ExpertDataset`**

By comparing the requirements from Phase 1 with the current implementation, we can identify the following gaps:

1.  **OCTO Model Dependency**:
    *   **Current State**: The `ExpertDataset` is fundamentally designed to use OCTO as the primary action generator, with the `ScriptedExpert` as a fallback. The `__init__`, `_init_worker_state`, and `_generate_one` methods are filled with OCTO-specific logic, model loading, and post-processing heuristics.
    *   **Gap**: This entire dependency is now obsolete. It introduces unnecessary complexity, failure points, and performance overhead (JAX/PyTorch interop). It must be completely removed.

2.  **Data Generation Paradigm (Sample vs. Chunk)**:
    *   **Current State**: The `__iter__` method generates a trajectory but then yields individual `(obs, action)` pairs one by one from an `_episode_buffer`.
    *   **Gap**: This is the most significant architectural gap. The entire iteration logic needs to be refactored from a sample-by-sample generator to a **trajectory-by-trajectory chunker**.

3.  **Action Space Duality**:
    *   **Current State**: The `_generate_one` method calculates both an `absolute_final_action` (to step the simulation) and a `delta_final_action` (to potentially yield).
    *   **Gap**: While it *can* produce the correct delta action, this duality is confusing. The new design must clearly separate the internal simulation action from the final data action to be saved.

4.  **Configuration and Usability**:
    *   **Current State**: The `__init__` method has many OCTO-related arguments (`octo_model_name`, `instruction`, `warmup`).
    *   **Gap**: The constructor should be simplified to only include parameters relevant to the `ScriptedExpert` and the new chunking mechanism (e.g., `history_len`, `future_len`).

### **Phase 3: Detailed Implementation Plan for `ExpertDataset` Refactoring**

This plan outlines the specific code modifications required, method by method.

**1. `ExpertDataset.__init__()` Method**
*   **Remove** all OCTO-related parameters: `octo_model_name`, `instruction`, `warmup`, `use_octo`. The `use_octo` flag will be removed entirely, making the `ScriptedExpert` the sole policy.
*   **Add** new parameters to control the data structure:
    *   `observation_horizon: int = 4`
    *   `action_horizon: int = 8`
*   Simplify the stored attributes, removing any that are OCTO-specific.

**2. `ExpertDataset._init_worker_state()` Method**
*   **Remove** the entire block responsible for loading the `OctoModel`, creating the `task`, and performing the JAX warmup.
*   The method will now only be responsible for initializing the `PandaEnv`, `IKSolver`, `ScriptedExpert`, and the worker-specific random seed. This will make initialization much faster and more reliable.

**3. `ExpertDataset._generate_one()` Method (To be renamed or removed)**
*   This method's role changes. It is no longer generating a single sample to be yielded. Instead, its logic will be integrated into a new method, e.g., `_generate_full_trajectory()`.
*   The core logic will be:
    1.  Call `self._scripted_expert.get_target_pose()` to get the target EE pose.
    2.  Call `self._ik_solver.compute_action()` to get the absolute joint action for the simulation.
    3.  Compute the corresponding delta action.
    4.  Return a tuple: `(observation, absolute_sim_action, delta_data_action)`.

**4. `ExpertDataset.__iter__()` Method (Major Refactoring)**
*   This method will house the new core logic.
*   **Step 1: Trajectory Generation Loop**:
    *   Enter a `while True` loop to continuously generate data.
    *   Inside the loop, call a new helper method `_generate_full_trajectory()` which executes an entire episode using the `ScriptedExpert`.
    *   This helper will return a list of `(obs, delta_action)` tuples *only if the episode was successful* (verified via `self._scripted_expert.was_successful()`). If not, it returns `None` and the loop continues to the next attempt.
*   **Step 2: Trajectory Chunking**:
    *   Once a successful trajectory (e.g., of length `L`) is obtained, iterate through it with a sliding window.
    *   The window will run from index `i = 0` to `L - action_horizon`.
    *   For each index `i`:
        *   Check if there is enough history (`i >= observation_horizon - 1`).
        *   **Gather Observation Chunk**: Collect the `observation_horizon` observations from `trajectory[i - observation_horizon + 1 : i + 1]`.
        *   **Gather Action Chunk**: Collect the `action_horizon` actions from `trajectory[i : i + action_horizon]`.
        *   **Stack and Format**: Stack the collected observations and actions into the final dictionary structure defined in Phase 1, converting them to PyTorch tensors.
        *   `yield` the resulting chunk dictionary.
